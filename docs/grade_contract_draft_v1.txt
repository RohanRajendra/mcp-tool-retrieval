PROJECT: SAMPLE DATA AND GRADE CONTRACT

TASK IN BRIEF
AI agents connect to many tool servers (MCP servers) at once. Different vendors ship near-identical tools with different names and descriptions, for example two filesystem servers that both move files. An agent cannot load every tool, so it must first retrieve a short list of the right ones for a request. Our task: given a plain-English developer request, rank tools pooled from many real MCP servers. Several tools can be correct, because equivalent tools from different vendors are equally relevant.

PART 1. SAMPLE DATA

How it was built
- Collection: 384 tools from 13 real MCP servers (filesystem, Git, GitHub, Postgres, Docker, browser, web fetch). Versions are pinned.
- Queries: 12 sample queries, written before reading tool descriptions.
- Candidates judged per query: the top 10 results of a BM25 keyword search, plus tools added by hand that can do the job but the search missed.
- Judging: relevance judgments were made by an LLM following a written rubric. A human check and a second-pass consistency check are part of the contract below.

Relevance scale
3 = does the request, or one required step of a multi-step request, by itself.
2 = does it partly, or only with extra steps.
1 = related, but cannot do the request.
0 = not relevant (not listed below).
Note: for multi-step requests, grade 3 means a tool fully does one required step. This is slightly broader than "accomplishes the whole request."

Server labels: FS-ref and Git-ref are the official reference servers. Other labels are the vendor or author name.

Early observation: BM25 alone often misses relevant tools. For queries 3 and 4, its top 10 contained 0 of the 5 relevant tools we found.

PART 2. GRADE CONTRACT
Each milestone is something we do, not a result we must reach.

B
- Collection of at least 300 tools from at least 6 categories, with server versions pinned and retrieval date recorded.
- 40 queries, each written before reading tool descriptions, each with a narrative stating what counts as relevant.
- Candidate pools built from BM25 plus one off-the-shelf retriever.
- Relevance judgments on the 0 to 3 scale from an LLM under a written rubric. LLM use is disclosed in the report.
- A BM25 baseline run on all queries and scored with nDCG@10 and Recall@k.
- Final report covering the task, queries, relevance criteria, and baseline results.

B+ (everything in B, plus)
- Hybrid retrieval: BM25 plus dense embeddings over tool name, description, and parameter schema, merged with reciprocal rank fusion.
- Comparison of BM25, dense-only, and hybrid on the same queries.
- LLM consistency check: a second LLM pass re-judges a sample of at least 100 query-tool pairs. We report weighted Cohen's kappa (a standard measure of agreement between two judges).

A- (everything in B+, plus)
- Equivalence groups: functionally equivalent tools across servers labeled together under a written rule, including how partial overlap is handled.
- α-nDCG over those groups (an nDCG variant that penalizes repeating the same function), plus an analysis of how much redundancy the baselines return.
- Human validity check: the team hand-judges at least 50 query-tool pairs, with extra weight on tools the LLM added by hand, and reports weighted kappa against the LLM judgments.

A (everything in A-, plus)
- A duplicate-aware reranker that detects equivalent tools and reorders results to cover distinct capabilities.
- Evaluation of the reranker against the hybrid system using α-nDCG, and nDCG@10 to show whether relevance is lost.
- Error analysis of where the reranker helps and where it fails.
- Scale-up to 50 queries and up to 500 tools, with 3 to 5 servers per category.

Stretch goals (not required for any grade): normalizing tool descriptions before indexing, and decomposing multi-step queries.

PART 3. BARRIERS
1. Reaching full collection scale. The collection is at 384 tools from 13 servers, below the 500-tool target. Some servers need credentials to start, and finding more runnable servers per category may take time. Plan: use dummy credentials to list tools, and fall back to the official README tool list, clearly labeled, when a server will not start.
2. Tool lists change by version. One source lists the official filesystem server with 12 tools and another with 14. Plan: pin every version and record the retrieval date.
3. Equivalence labeling is subjective. Tools can overlap only partly, for example one reads a whole file while another also supports reading the first or last lines. Plan: a written rule for what counts as equivalent, with a defined partial case.
4. Running third-party servers is a security risk. Plan: run all servers in a container, with no access to personal files or credentials.
